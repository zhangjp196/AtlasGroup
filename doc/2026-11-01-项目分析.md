## 核心链路（实测读代码确认）
1. **HTTP → 队列**：`POST /conversations/{id}/messages/run` 落 GDAG 消息节点 + `conversation_runs`（status=queued），HTTP 立即返回，不等模型。
2. **worker**：`conv_worker.ConversationRunWorker` 进程内循环（`CYCLE_INTERVAL_S=1`），`claim_run` 用 CAS 单写防双跑；`_TICK_S=0.5` 轮询预取任务，静默期自己补 20s `ping`；`force_stop` 直接取消任务 + 杀同会话后台工具 + `_STOP_GRACE_S=3` 兜底强制收尾。
3. **对话循环**：`conversation._stream_role`（约 1474 行）一轮 = 一次模型往返 + 它调用的工具；串行类工具（`_SEQ_CALLS_TOOLS`）走专有分支不进并发批；计划步骤按 `depends_on` 就绪推进，未完成会持续催促（`_MAX_PLAN_NUDGES=0`、`_MAX_TURN_ROUNDS=0` = 不限）。
4. **事件落库 + 推送**：每条事件写 `conversation_run_events(run_id, seq)`，进程内总线即时推 SSE，断线按 `since=seq` 从库 replay；delta 按 120 字符 / 100ms 合并。
5. **权限**：`permissions.classify` 按工具基风险 + shell/python 正则特征升档；`MODES = auto/once/session/always`；写 `hooks.json` 强制人工确认（不受 Allow 影响）；审批落 `tool_approvals`，进程内事件 + 库兜底等待决策，重启时 `expire_orphan_approvals` 清理。
6. **上下文**：两级压缩（先 prune 旧工具输出成一行，再调摘要模型出 `<conversation-checkpoint>` + 保留 15k 原文）；触发点 = 窗口 − max(15% 窗口, 16000)；跨轮历史另有 60 条 / token 预算双上限；超大工具输出（>40000 字符）落 `.atlas/tool-output/`，上下文只留预览+路径。
7. **工具组织**：7 个包（fs/net/memory/plan/dev/skill/mcp）用 `op` 选动作 + 独立工具 shell/workspace/ask_user；旧包名与旧工具名保留兼容解析（`packs.resolve_call`）。

## 工程亮点（值得保留）
- **不假死的流式**：所有正常等待必须每 20s 出一条事件；`stream_idle_timeout_s` / `run_event_stall_s` 默认 0 = 不中止（长任务误判比漏判贵，这是踩坑后的结论）。
- **落库韧性**：`database is locked` 自动重试；启动时 DB 完整性 preflight + 损坏从备份恢复 + 每日备份 + 7 天事件清理。
- **LLM 稳定性**：按渠道共用连接池（不每次重做 TLS）、重试 20 次 × 2.5s 固定退避 + `retry_deadline_s=900` 总上限、429 取 `Retry-After`。
- **路径安全**：`resolve_workspace_path` 用 `resolve()` + `relative_to()` 挡路径穿越，所有文件工具与 `/workspace/*` 共用。
- **密钥**：macOS Keychain 优先，sqlite 只存 `keychain:<ref>` 占位符，诊断包脱敏。
- **检查点回退**：sha256 去重 blob + 清单，回退前预览新增/修改/删除，超限标记不完整且不删新增文件。

## 风险与欠账（按优先级）
1. **`task_layer/conversation.py` 5611 行、`_stream_role` 单函数约 1517 行**（conversation.py:3417-4933，2026-11-02 复核）。全项目的对话循环、计划推进、审批等待、子代理委派、压缩事件都在这一个函数里，改任何一处都要通读千行；这是最大的维护风险。
