## 0. 一句话结论

现在系统里有**三套重叠的多角色机制**，其中两套是死代码：

| 机制 | 载体 | 是否可达 |
| --- | --- | --- |
| 群组工作区多角色 | `workspaces.kind='group'` + `host_role_id` / `member_role_ids` | **不可达**：所有工作区 `member_role_ids` 只有 `["default"]`，没有 UI 能加成员 |
| 群组多角色应答 | `_group_reply_stream` + `@提及` + `GROUP_MAX_SPEAKERS=4` | **不可达**：`conversation_runs.mentions` 全库 0 条非空，`MessageBody` 没有 `mentions` 字段 |
| Agent 团队 | `agent_teams` + `conversations.team_id` + `delegate(target=team)` | **可达但只有模型能建**：没有 REST 路由、没有 UI，40 条 `team.*` i18n 是死文案 |

3.0 的实质不是改名，而是：**把「团队」提升为一等公民（可 UI 创建、可 REST 管理、可会话绑定），把「群组」语义收敛进团队，把「角色」变成可配置的一等实体。**

界面上，3.0 也不再是 vibecoding 工作台：**会话列表 + 聊天窗**就是全部骨架（QQ 式 IM），团队在界面上叫「群」，文件/计划/diff/终端都是会话内的卡片与抽屉（详见 §7）。

## 1. 现状实测（关键事实）

1. **角色表只有 1 个真实角色 + 动态 teamrole**
   `roles`: `default`(Atlas) + 8 个 `teamrole-*`（架构主持/后端/测试/前端/编排者/调研员/记录员），全部由 `team_manage` 创建。
   没有角色 CRUD 路由（`grep "roles" routes/*.py` 只有 `DEFAULT_ROLE_ID` 引用）。

2. **团队完全由模型动态创建**
   `team_service.py:5` 注释明确「没有界面配置入口」；`app.js:5910` 注释同样确认。
   `registry.py:528` 工具描述：「界面没有团队配置入口——团队完全由你按任务需要定义」。

3. **成员角色能力包络完全相同**
   `_ensure_role()` → `envelope = dict(zero_store.DEFAULT_ENVELOPE)`，所以「后端工程师」和「测试工程师」工具集、网络策略、可写路径**完全一致**，只有 `persona`/`expertise` 文本不同。

4. **上限不一致且硬编码**
   `GROUP_MAX_SPEAKERS = 4`（conversation.py:431）vs `_MAX_MEMBERS = 12`（team_service.py:21）。

5. **文档与行为矛盾**
   `registry.py:465` 说「子代理不能再嵌套子代理」，但 `_SUBAGENT_MAX_DEPTH = 0` → 条件 `if _SUBAGENT_MAX_DEPTH and ...` 恒假 → **实际不限嵌套**。

6. **死字段 / 死表**
   - `workspaces.zones`：全库 0 条非空，代码只读写不消费。
   - `workspaces.kind` 的 `'task'` / `'role'`：只有 `_resolve_chat_role` 的 `kind == 'role'` 兜底分支和 `workspace_service.WORKSPACE_KINDS` 校验用到；创建路径全部写 `'group'`。
   - `task_blueprints` 表：模型已下线（r1181），表还在，3 行残留数据。
   - `conversation_runs.mentions`：写入路径存在，前端从不传。

7. **团队执行路径**
   `conversation.py:2627` 绑定团队 → 主持角色 `_single_reply_stream`；委派走 `_exec_call_team` → `_exec_call_agent`（isolated，不继承父团队/目标）。流程图 `worker=team` 有渲染（`app.js:5747/5867`）。

## 2. 目标模型

### 2.1 概念统一（对外只讲「角色」和「团队」）

| 概念 | 定义 | 载体 |
| --- | --- | --- |
| **工作区** | 一个对话容器 + 可选工作目录 | `workspaces`（`root_path` 决定 chat-only） |
| **角色** | 一个可执行的人格：persona + expertise + 能力包络 + 模型档案 | `roles` |
| **团队** | 一组角色 + 一个主持 + 一种协作模式 | `agent_teams` |
| **会话** | 属于一个工作区，可选绑定一个团队 | `conversations.team_id` |

`Workspace.kind` 删除（V3 不需要兼容），行为由 `root_path` 决定；工作区成员归属完全由 `agent_teams` 表达。

### 2.2 三种协作模式（`agent_teams.mode`）

| mode | 语义 | 执行 | 对应现有代码 |
| --- | --- | --- | --- |
| `orchestrate`（默认） | 主持编排，成员被委派 | 主持 `_single_reply_stream` + `delegate(target=team)` | 现有行为，保持不变 |
| `roundtable` | 多角色各自应答，`@成员` 触发 | `_group_reply_stream` | 把 `_group_roles` 改为读团队，不再读 workspace |
| `single` | 团队只是角色预设，不协作 | 指定角色直接跑 | `_resolve_chat_role` 的 role 分支 |

这样 `_group_reply_stream` 从「不可达的死代码」变成「roundtable 模式」，而不是删掉。

### 2.3 数据模型

V3 直接定义基线 schema（见 §3），不做 `ALTER` 增量迁移，也不回填旧数据。

### 2.4 角色能力包络差异化（当前缺失的关键能力）

`_ensure_role` 现在一律 `DEFAULT_ENVELOPE`。改成：

```python
def _ensure_role(ws_id, role_id, name, expertise, envelope=None, model_code=None):
    env = dict(DEFAULT_ENVELOPE)
    if envelope:                      # 用户/模型显式给的工具子集
        env["tools"] = [t for t in envelope["tools"] if t in known_codes()]
    ...
```

并让 `delegate` 的 `tools` 参数对**团队成员**同样生效（现在只有 subagent 有 `_narrow`）。这样「测试工程师只跑 shell + fs」成为可配置事实，而不是 prompt 里的口头承诺。

## 3. V3 基线 schema（不做增量迁移）

既然不需要兼容旧数据，`database.py` 里那套「按版本号补列」的机制可以整体删掉：`_ensure_columns()`（15 个 `ALTER TABLE`，含 `priority → queue_pos` 的插队迁移）、`_apply_migrations()` 骨架、`schema_meta` 表都可以换成一个更简单的版本守卫。

> **落地进度（2026-11-02 复核，2026-11-03 修正）**：`database.py` 里 `SCHEMA_VERSION = 3`、
> `_ensure_columns` / `_apply_migrations` 已删除、版本守卫 `_guard_old_database`（读 `schema_meta.checksum`，
> 不匹配则备份成 `.v2.bak`）已写。**但「删列 / 重建库」的路线已被 V3 口径取代**：为保留现有群组数据，
> `workspaces` 的群组列（`kind` / `host_role_id` / `member_role_ids` / `zones` / `origin`）已恢复并与真实 SQL 对齐；
> `roles` 仍是 `group_id`（未改 `workspace_id` / `team_id`）；`agent_teams` 的 `mode` / `max_speakers` 尚未加回。
> V3 改为「增量加列 + 惰性归一、不重建库」，见 [V3 目标与收尾](2026-11-03-AtlasX-V3-目标与收尾.md) §4。
> 下列「收尾没做完」是当时的状态记录：
>
> 1. `database.py` 缺 `import threading` → 模块级 `_session_factory = threading.local()` 直接 `NameError`，`import services.agent_zero.database` 就失败。
> 2. 缺 `get_db_schema()` / `get_schema_version()` → `gdag/store.py:19`、`gdag/retrieve.py:21`、`memory_service.py:35/358/414/501`、`metrics_service.py:169` 仍在 import，`ImportError`。
> 3. `schema_meta` 表没有任何 ORM 模型或建表语句（`models/zero.py` 只有 15 张业务表，`grep schema_meta` 只命中 `database.py`），守卫里的 `SELECT checksum FROM schema_meta` 会直接报 `no such table`。
> 4. 旧库 `data/agent_zero/agent_zero.db` 仍是 v1 结构（`schema_meta` 只有 `id/version/updated_at`，无 `checksum`；`workspaces` 仍有 `kind`/`zones`），按守卫逻辑会被备份重建。
>
> 下面 §3.2 的 DDL 与当前 `models/zero.py` 一致（`roles` 用 `workspace_id` 而不是 `group_id`；但 `zero_store.py` 的 SQL 仍在写 `group_id`，见 §5）。

### 3.1 直接删除的死字段 / 死表

| 对象 | 现状 | V3 动作 |
| --- | --- | --- |
| `workspaces.zones` | 全库 0 条非空，代码只写不读 | 删列 |
| `workspaces.member_role_ids` / `host_role_id` | 全部只有 `["default"]`，无 UI 可改 | 删列（成员归属由 `agent_teams` 表达） |
| `workspaces.kind` | 只有 `'group'` 被创建路径写入；`'task'`/`'role'` 只在两个兜底分支用到 | 删列，行为改由 `root_path` 决定 |
| `workspaces.origin` | 只有 folder-picker 写入，无消费 | 删列（或保留做审计，二选一） |
| `conversation_runs.priority` | 已被 `queue_pos` 取代，旧库残留 | 不再补列，直接不存在 |
| `task_blueprints` | 模型已下线（r1181），表残留 3 行 | 不建表 |
| `roles.group_id` | 历史名，语义 = workspace_id | 改名 `workspace_id`，并加 `team_id` |

### 3.2 V3 基线（一次性建表，无 ALTER）

```sql
-- workspaces：只保留真正被消费的列
CREATE TABLE workspaces (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  root_path TEXT,
  default_team_id TEXT REFERENCES agent_teams(id) ON DELETE SET NULL,
  archived BOOLEAN NOT NULL DEFAULT 0,
  created_by TEXT NOT NULL DEFAULT 'local',
  created_at DATETIME NOT NULL DEFAULT (datetime('now','localtime'))
);

-- roles：角色成为可执行实体（包络 + 模型档案 + 归属）
CREATE TABLE roles (
  id TEXT PRIMARY KEY,
  workspace_id TEXT REFERENCES workspaces(id) ON DELETE CASCADE,
  team_id TEXT REFERENCES agent_teams(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  persona TEXT,
  expertise TEXT,
  avatar TEXT,
  envelope JSON NOT NULL DEFAULT '{}',
  model_code TEXT,
  is_system BOOLEAN NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT (datetime('now','localtime'))
);

-- agent_teams：团队 = 主持 + 成员 + 协作模式 + 上限
CREATE TABLE agent_teams (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  description TEXT,
  mode TEXT NOT NULL DEFAULT 'orchestrate'
    CHECK (mode IN ('orchestrate','roundtable','single')),
  max_speakers INTEGER NOT NULL DEFAULT 4 CHECK (max_speakers BETWEEN 1 AND 12),
  leader_role_id TEXT REFERENCES roles(id) ON DELETE SET NULL,
  member_role_ids JSON NOT NULL DEFAULT '[]',
  created_at DATETIME NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at DATETIME NOT NULL DEFAULT (datetime('now','localtime'))
);
```

其余表（`conversations` / `conversation_runs` / `conversation_run_events` / `gdag_nodes` / `gdag_edges` / `audit_logs` / `app_settings` / `tool_approvals` / `permission_grants` / `todo_items` / `goals` / `skills`）结构不变，只是 `conversations.team_id` 加 FK。

`GROUP_MAX_SPEAKERS = 4`（conversation.py:431）与 `_MAX_MEMBERS = 12`（team_service.py:21）合并成 `agent_teams.max_speakers` + 全局上限常量，不再两处硬编码。

### 3.2.1 必须处理的工程细节（实测确认）

`Base.metadata.create_all()`（database.py:295）**不会修改已存在的表**。所以「删列」在旧库上不会生效 —— 旧库的 `workspaces` 仍然有 `zones`/`kind` 等列，新代码读 `SELECT *` 时会拿到多余列（无害），但新加的 `mode` / `max_speakers` 列**不存在**，`team_service` 读它会直接报错。

因此 V3 启动时必须做版本守卫，三选一（建议第 2 条）：

1. 保留一个极简 `schema_meta` 表，`SCHEMA_VERSION = 3`；版本不匹配 → 明确报错并提示删除 `data/agent_zero/agent_zero.db`。
2. 版本不匹配 → 自动把旧库重命名为 `agent_zero.db.v2.bak`，建新库，日志提示「V3 数据结构变更，旧数据已备份」。
3. 什么都不做（最危险）：旧库静默运行，团队功能随机报错。

另外 `_register_sqlite_functions()`（database.py:98-143）注册的 `now()` / `to_jsonb()` / `jsonb_set()` 三个 PG 兼容函数仍在被 20+ 处 SQL 使用（`run_service.py:306/425/430/466/487/501/542/576/649`、`conversation.py:554-562/2782-2824`）。V3 可以保留（成本低），但这是「历史兼容」残留，顺手清理成纯 sqlite 写法更干净。

## 7. 界面定位：不是 vibecoding 工作台，是 IM 客户端

### 7.0 V3 界面不做什么（这是定位，不是待办）

V3 **刻意不做**传统 vibecoding 工具那套工作台：不要「文件树 + 代码编辑器 + 终端 + diff 三栏并排」，不要常驻的 IDE 侧边栏，不要以「项目 / 会话 / 分支」为中心的组织方式。

V3 的界面模型是 **QQ 这类 IM 客户端**：左边一个会话列表，右边一个聊天窗，其余一切（文件、计划、diff、终端、记忆）都是**会话内的消息卡片**或**点开才出现的抽屉**。用户的心智是「在跟谁聊」，不是「在哪个工程里操作」。

一句话：**对话是唯一的入口，工程能力是对话的附件。**

### 7.1 信息架构对照（QQ → Atlas Group）

### 7.2 关键取舍：vibecoding 元素在 IM 里的归宿

不是「删掉功能」，而是**换承载方式**：

| --- | --- | --- |
| 右侧 dock：Workspace 文件树 / Viewer 代码编辑 / VCS diff / Memory / CodeGraph | **不再默认展开**。文件、diff、记忆、图谱都从**消息卡片**点进：点「改了 3 个文件」展开成 diff 卡片，点文件名在**会话内抽屉**预览 | 抽屉复用现有 `panel-viewer` 的渲染，但去掉「常驻 dock + 编辑态」的定位；`viewerEditBtn` / `viewerSaveBtn`（`index.html:429-430`）在 V3 降为「只读预览 + 复制」，写文件交给 Agent 的工具调用 |
| 顶栏 6 个图标按钮（workspace/vcs/todo/plan/codegraph/mem） | 收进**会话信息抽屉** + 输入框上方的**上下文行**（进程 / 任务 / 目标 / 计划各一个 chip，跑完自动消失） | `chat-floats` 里的 `processPanel` / `todoPanel`（`index.html:219/229`）已经是这个思路，V3 把它做成唯一形态 |

### 7.3 团队在 IM 里的表达（补 40 条死 i18n 的落地）

现有 `team.*` 20 条英文 + 20 条中文 key 已经写好了（`app.js:596-615` 英文 / `1693-1712` 中文，各 20 条），只是没有 DOM。IM 语义下不需要「团队管理面板」，需要的是**群**：

1. **新建会话时选「单聊 / 群聊」**：单聊 = 选一个角色（`single`）；群聊 = 选一个团队（默认 `orchestrate`，群里只有主持说话、成员在委派卡片里干活；切到 `roundtable` 才是多头像各自应答）。对应 `agent_teams.mode`。
2. **会话标题 = 群名**，副标题显示「主持 + N 人」；点标题打开**会话信息抽屉**（`panel-conv`，新增）：
   - 群名 / 简介 / 协作模式（编排 / 圆桌 / 单角色）
   - 成员列表（头像 + 名字 + 专长 + 工具子集），支持增删（写 `POST/PATCH /teams/{id}`，见 §6）
   - 「使用该团队的角色直接应答」= `roundtable` 开关
3. **进群第一条系统消息**：「主持把「后端」加入群聊」这类系统提示，写普通 `fact` 记录、`by='system'`，比一个配置面板更符合 IM 心智。
4. **`@成员` 补全 + `mentions` 打通**：composer 里 `@` 列出群成员（复用 slash menu 机制 `updateSlashMenu`，目前只匹配 `^/`，`app.js:10917`）；`MessageBody` 加 `mentions: Optional[List[str]]`，`run_service.create_run` 已支持（`run_service.py:44`）。
5. **成员状态 = 气泡上的角色名**：roundtable 模式下每条 Agent 消息本来就带 `role_name`，等于群聊里每个人的昵称；编排模式下只看主持，成员的活动在**委派卡片**（`subagentBar` chip）里体现。

**不做**：把团队配置塞进「设置」的一个 tab。设置页是 IM 的「系统设置」，团队是「群资料」，两者不该混。

### 7.5 与其它章节的一致性

- §2.2 的三种 `mode` 在界面上只剩两个用户可见概念：**单聊**（`single` / `orchestrate` 对话时看主持）与**群聊**（`roundtable` 多头像发言）。`orchestrate` 与 `single` 的差别对用户不可见，不需要在 UI 暴露。
- §6 的 REST 接口不用改，只是消费方从「设置面板」变成「会话信息抽屉」。
- §11 风险 1（roundtable 成本）在 IM 形态下更容易表达：群聊输入框上方显示「本群 4 个角色，每条消息最多 4 次模型调用」，比一个配置项里的 `max_speakers` 直观。

## 11. 风险

1. **roundtable 模式一旦可达，成本立刻可见**：多角色 = 多次 LLM 调用，`max_speakers=4` 意味着一次用户消息最多 4 次完整工具循环。必须在 UI 明确「这是多角色圆桌，不是单 agent」。
2. **角色删除语义**：`delete_team` 会删成员角色；若同一角色被两个团队共用，删一个团队会删掉另一个团队的成员。基线 schema 里 `roles.team_id` 让归属唯一化，但需要显式「共享角色」概念（建议：系统角色不删，团队角色按 team_id 删）。
3. **旧库静默运行**（实测确认）：`create_all()` 不改已有表，旧库缺 `mode` / `max_speakers` 列会让团队功能随机报错。版本守卫必须落地，不能省略。
4. **改名波及面大**：2079 处 `agent_zero` 引用（含 `dev.sh`/`start.sh`/`stop.sh`/`init_db.py`/`Atlas.spec`/测试），一次改错会让启动脚本与打包 spec 不一致。建议 P3 独立提交并跑完整 CI。
5. **未验证项**：本设计只做了静态与数据实测（源码 grep + sqlite 查询 + `_group_roles` / `_chat_tool_specs` 实际调用），没有跑端到端多角色对话。
6. **IM 化会削掉重度用户的工作效率**：把常驻 dock 收成抽屉，对「一边改代码一边看 diff」的用法是净损失。V3 的取舍是「把重度用户推回 IDE、Atlas 只当协作方」；如果实际用户画像不是这样，§7.2 的「抽屉化」应降级为「默认收起、可固定展开」。
7. **未读计数需要新状态**：`conversations` 现在没有任何已读/未读字段（grep 确认），加 `last_read_at` 会让 `list_conversations` 多一次写（切换会话时更新），要注意 SQLite 写锁与 `claim_run` 的 CAS 争用。建议挂在「会话打开」而非「消息到达」上。
8. **schema 已改、读写代码没跟上（实测）**：`zero_store.create_workspace` 仍在 INSERT `kind` / `zones` / `origin`（`zero_store.py:83`），而 v3 的 `workspaces` 已没有这些列 → 建工作区会直接 `no such column`；`_group_roles` 仍用 `ws.get("kind") != "group"` 判断（`conversation.py:440`），v3 里恒为 `None` → 群组分支永久不触发。这两处必须在 P1 一起改，否则「schema 迁移完成」等于没完成。
