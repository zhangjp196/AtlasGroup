# 性能优化：会话列表 / 注意力面板 / 首屏包体（2026-11-09）

> 结论先行：这轮最值钱的是「会话列表 3.6s → 17ms」。前端包体从 569KB 降到
> 324KB，长会话改成窗口化渲染。所有数字都在同一台机器、同一份合成数据上测。

## 方法

先量再改，避免凭感觉优化：

1. **后端**：把 `data/agent_zero/agent_zero.db` 复制到 `/tmp`，灌一份合成数据
   （300 会话 / 10,240 条 gdag 消息 / 3,000 个 run / 36,000 条事件 / 500 工单），
   用独立端口起服务，`curl` 采样 20 次取 p50/p95；再用 `cProfile` 定位到具体
   SQL 与 Python 调用。
2. **前端**：`vite build` 看产物；`vue-tsc` + `vitest` 保证不回归；用 headless
   Chrome（CDP）加载每个路由，确认没有「组件未解析」和明显报错。
3. **数据库**：`EXPLAIN QUERY PLAN` 确认索引是否真的被用上。

## 根因与改动

### 1. 会话列表：3 个相关子查询 × 每个会话扫全表

`task_layer/conversation.py::list_conversations` 原来在主查询里对每一行算
「未读数 / 未读条数 / 最近助手消息时间」，写法是：

```sql
(SELECT COUNT(*) FROM gdag_nodes g
  WHERE g.type = 'fact' AND g.props->>'conversation_id' = c.id ...)
```

两个问题叠加：

- **相关子查询**：300 个会话就执行 300 次，每次扫 `type='fact'` 的全部行；
- **`props->>` 命中不了表达式索引**：`ENSURE_INDEXES` 里的索引建在
  `json_extract(props, '$.conversation_id')` 上，SQLite 不会把 `->>` 当成等价
  表达式。`EXPLAIN QUERY PLAN` 显示实际走的是 `idx_gdag_type (type=?)`——等于全表扫。

改法（`_page_message_stats`）：

1. 主查询只取分页需要的列（`running_count / run_status / goal_status / is_live`
   都走 `conversation_runs`、`goals` 的普通索引，3ms）；
2. 拿到这一页的 50 个 id 后，用一条 CTE 聚合算未读（`VALUES (id, last_read_at)`
   把每个会话的已读水位带进去），再用一条窗口函数查询取每个会话的最后一条消息；
3. 两条 SQL 都显式 `INDEXED BY idx_gdag_conv`，只扫本页会话的消息。

顺带把 `count_conversations` 的关键字过滤也改成 `json_extract` 写法。

### 2. 注意力面板：同一个反模式

`services/attention_service.py::unread_conversations` 也有 3 个相关子查询，
300 会话 ≈ 1s。改成：

- `WITH last_seen AS (SELECT json_extract(...), MAX(created_at) ... GROUP BY cid)`
  一次分组聚合，再 JOIN 会话表过滤；
- 未读条数 / 最后一条预览复用 `_page_message_stats`。

### 3. 用量聚合：`->>` 换 `json_extract`

`services/usage_service.py::_usage_agg_sql` 的 `props->>'{column}'` 同样命中不了
`idx_gdag_conv` / `idx_gdag_run`，改成 `json_extract(props, '$.{column}')` 后
内部耗时 ~10ms → ~5ms。

### 4. 入口包：Element Plus 不再全量注册

`main.ts` 原来 `import` 29 个组件并 `app.use()`，等于把设置页才会用到的
`ElTree / ElCascader / ElMenu` 也塞进首屏。改成每个用到 `<el-*>` 的 SFC 自己
`import { ElButton } from 'element-plus'`（`script setup` 会自动暴露给模板），
由 Rollup 按路由 chunk 拆。

- 入口 JS：569KB → 324KB（gzip 204KB → 125KB）；
- 组件样式仍统一在 `main.ts` 引入，避免 24 个文件各写一遍 `style/css`；
- 用 headless Chrome 打开 `/work /conv /role /group /ws /settings /about`，
  DOM 里没有残留 `<el-*>` 标签（组件全部解析成功）。

### 5. 长会话：消息列表窗口化

`ChatPanel.vue` 原来一次渲染全部消息（接口上限 200 条）。改成默认只建最近
60 条，顶部给一个「显示更早的 N 条消息」，点开再补 60 条：

- 展开时以「当前窗口第一条消息」为锚点，用 `getBoundingClientRect` 差回补
  `scrollTop`，视线停在原来那条消息上（比记 `scrollHeight` 差值稳，Markdown /
  图片高度是异步撑开的）；
- 切换会话时窗口重置回 60。

200 条消息的 DOM 从 3,895 降到 2,630。

### 6. 启动动画：从固定 5 秒改成「数据就绪就收」

`App.vue` 的启动动画原来是 `duration=5000` 固定播满 5 秒（可点击跳过），
但首屏数据（工作区 / 会话 / 角色 / 团队 / 模型 / 工单）在 300ms 左右就加载完了，
用户要白等 4 秒多。改为：

- `onMounted` 里 `Promise.all([loadAll(), loadWork()])` 结束后置 `bootReady`；
- 动画收到 `ready` 后，只要已播满 900ms 就提前收尾（保留 460ms 退场）；
- 加载失败也会放行（`finally`），慢机器上仍然是完整 5 秒兜底，不会更差。

实测界面可用时间：约 5,000ms → 1,420–1,680ms（headless Chrome 真实时间）。
这是本轮**体感最强**的一项——首屏资源再快，也快不过一个固定 5 秒的动画。

### 7. 复合表达式索引：`(conversation_id, stage, created_at)`

跨轮取历史（`_history_messages`）、转录（`list_messages`）、检查点都是
「按会话 + 阶段过滤，再按时间倒序取 N 条」。只有 `(conversation_id, stage)`
两列索引时，SQLite 能把范围缩小，但仍要把这些行取出来排序。

新增第三个索引列 `created_at` 后，可以「沿索引倒序扫 + 提前 LIMIT」，
`EXPLAIN QUERY PLAN` 里的 `USE TEMP B-TREE FOR ORDER BY` 消失。

索引同时声明在 ORM 模型上（`Index(..., text("json_extract(props, '$.conversation_id')"), ...)`）
和 `ENSURE_INDEXES` 里：前者保证 `create_all` 建的库（测试 / 脚本）也有，
后者给已有库补建。

**踩到的坑**：一开始用 `FROM gdag_nodes INDEXED BY idx_gdag_conv_stage_created`
强制走新索引，结果老库 / 测试库没有这个索引时直接
`no such index` 崩掉。改成不硬绑索引——`(conversation_id, stage)` 索引已经能把
「全表扫」变成「扫本会话」，排序几百行的代价可以忽略。

### 8. `usage_total` / `_latest_user_prompt` / 干预读取：还是 `->>`

这几个每轮都会跑的查询仍在用 `props->>`，命中不了表达式索引：

- `usage_total`：19.6 ms → 1.5 ms（其中「最近一轮 prompt」那条强制走
  `idx_gdag_conv_stage`，否则规划器会去扫 `idx_gdag_type`）；
- `_latest_user_prompt`：约 10 ms → 0.07 ms；
- `_drain_new_interventions`（执行循环里每轮取干预）：约 10 ms → 1.8 ms。

### 9. 用量页：过滤下推到 SQL

`usage_service._load_events` 原来 `SELECT props FROM gdag_nodes WHERE type='fact'`
把**所有**节点取回 Python 再筛「助手消息 + 有 usage」。改成 SQL 里就用
`json_extract(props,'$.by')='assistant' AND json_extract(props,'$.usage') IS NOT NULL`
过滤，走 `idx_gdag_by` 表达式索引：32 ms → 7.5 ms，且不再随历史线性变慢。

### 10. 工单详情抽屉改异步加载

`TaskWindow` 静态引入 `WorkSettingsDrawer`，连带把 Markdown（markdown-it）、
对话框、表单等一大串依赖拖进入口包。改成
`defineAsyncComponent(() => import(...))` + `v-if="workDetail"`：
入口 JS 323.8 KB → 105.9 KB（gzip 125.2 KB → 39.6 KB），首屏只需再多载一个
`vue` chunk（117 KB），聊天面板等仍然按需加载。

## 试过但不采用

- **`content-visibility: auto` + `contain-intrinsic-size`**：以为能让屏幕外消息
  跳过布局，实测反而更慢（同一页面 task 414/494ms → 558/756ms）。消息高度差异大，
  浏览器反复做尺寸估算 + 进入视口时重排，得不偿失。已回退。

## 验证

- `pytest tests/unit tests/integration` 全绿（533 passed）；
- `vitest run` 42 个用例全绿；`vue-tsc --noEmit` 通过；
- 合成数据下用旧实现逐条比对 `message_count / last_message / unread /
  unread_count`，300 条会话 × 2 种过滤 0 处不一致；空会话、归档、分页、关键字
  过滤单独回归；
- headless Chrome 验证窗口化：60 → 120 条，锚点消息位置保持。

## 还可以做（未做，按收益排序）

1. **真正的虚拟滚动**：现在只是「分批展开」，DOM 仍有 60 条下限；消息高度不固定，
   要做动态高度的虚拟列表（参考 Vue 官方性能指南的 list virtualization）。
2. **路由级 CSS 拆分**：入口 CSS 仍有 313KB，Element Plus 组件样式可按 route chunk 拆。
3. **消息表继续变大后的索引**：`(conversation_id, stage, created_at)` 复合表达式索引
   可以把「取最后一条消息」也变成覆盖索引；目前 1 万条消息量级还不需要。
4. **`loadAll()` 去重**：每次打开会话都会并发拉 6 个列表接口，可加短 TTL 缓存。
5. **`/app/attention` 19 ms**：9 条查询里最贵的是给 100 个未读会话算消息数/预览，
   可以只算前 20 个（面板本来也只看得到这么多）。
6. **文件检查点 `/checkpoints` 11 ms**：读磁盘上的 manifest 文件，可加进程内缓存。
