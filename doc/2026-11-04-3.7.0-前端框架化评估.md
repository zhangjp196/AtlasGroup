# 3.7.0 前端框架化评估（Vue / React + npm）

> 2026-11-04 · 评估对象：`VERSION = 3.6.0` 的前端现状与 3.7.0「静态前端 → Vue/React + npm」提案
> 方法：静态核对代码、测试、打包脚本与文档；行数与调用点为当前仓库实测。
> 结论先行：**方向总体更优，但前提是把 3.7.0 定义为「可回滚的分阶段迁移」，而不是一次性重写。**
> 框架选型建议：**Vue 3 + Vite + TypeScript + Pinia + Vue Router**（团队已重度使用 React 时改选 React，不混用）。
>
> **实施状态（2026-11-04）**：P0/P1 已落地，UI 采用 Element Plus（表单 / 弹框 / 设置 tabs / 按钮 / 标签 / 统计卡 / 组织树；聊天时间线保留自定义），源码在 `frontend/`，构建到 `web/dist`，后端直接挂在 `/`；旧 V3、`/classic`、`/next` 已全部移除。
> 已包含主壳、单聊/群聊聊天主路径、工作区、角色/群组、工单、设置、MCP/技能/命令、执行画布、全局Agent。`bash devops/ci.sh` 已接入前端 typecheck / Vitest / build，当前 423 pytest + 10 Vitest 通过。

## 1. 一句话判断

当前的问题不是「静态前端」本身，而是**两套前端 + 手写 DOM + 源码文本测试**已经到拐点：

- `web/v3` 是默认入口，但设置页仍用 `<iframe src="/classic?settings=1">` 内嵌旧前端；
- 旧前端 `web/assets/app.js` 仍有 **16,873 行**，为了设置页必须继续维护；
- 新壳 `web/v3/app.js` **5,691 行**，90 处 `innerHTML`、177 处 `addEventListener`、354 处 `S.` 状态访问；
- `tests/js/` 45 个测试文件（CI 接入 37 组），绝大多数是**源码字符串断言**（例如 `JS.includes("function switchTo(")`），不是行为测试；
- 改一处 UI 要同时考虑两套 CSS / i18n / 品牌注入 / 缓存戳。

在这个规模上，引入成熟框架的收益已经大于成本；但如果 3.7.0 直接「停旧写新、一次切换」，风险主要不在框架，而在**聊天流式渲染与设置页的回归覆盖不足**。

## 2. 现状量化

| 项 | 现状 | 说明 |
| --- | --- | --- |
| 默认入口 | `web/v3/` | `webapp.py` 的 `/` 指向 `web/v3/index.html` |
| 旧前端 | `web/index.html` + `web/assets/app.js` | 仅 `/classic?settings=1` 使用，但仍完整打包 |
| 新壳规模 | `web/v3/app.js` 5,691 行 / 264 KB；`app.css` 954 行 / 88 KB | 单个 IIFE，无模块边界 |
| 旧前端规模 | `web/assets/app.js` 16,873 行 / 708 KB；`app.css` 7,614 行 | 设置页仍依赖 |
| DOM 写法 | 新壳 90 处 `innerHTML`、177 处 `addEventListener`、173 处 DOM 创建/写入 | 每次渲染后重新绑事件，易漏解绑 |
| 状态 | 新壳 354 处 `S.` 直接读写 | 无响应式边界，靠手工 `render*()` 同步 |
| API 调用 | 新壳 22 个固定路径 + 45 个模板路径 | 手写字符串，无类型约束 |
| 前端测试 | `tests/js/` 45 个文件（CI 接入 37 组） | 绝大多数是源码文本断言；少量 headless Chrome 布局实测 |
| 构建 | 无 | 仅 `node --check web/assets/app.js` |
| 缓存 | 手写 `?v=3.6.0-3` | 每次发版手动改 `index.html` |
| 打包 | PyInstaller 直接收 `web/` | 没有前端构建步骤，也没有产物新鲜度检查 |

### 2.1 为什么「零构建」曾经是对的

这个项目是本地单用户、离线可用、无登录的桌面应用。零构建带来的是：

- 没有 `node_modules`、没有供应链、没有构建机；
- 改完 `web/` 刷新浏览器即可，打包脚本简单；
- 后端直接托管静态文件，运行时不依赖 Node；
- 出问题时可以直接读源码，排查链路短。

这些优点在 3.0 之前是净收益。**转折点不是框架流行，而是设置页开始内嵌旧前端、聊天/工单/画布/群聊都进入同一个 IIFE。** 从这里开始，零构建的维护成本开始指数上升。

### 2.2 真正的痛点排序

1. **两套前端必须同时维护**：品牌、主题变量、i18n、缓存戳、设置页交互都要改两遍；旧前端为了一个 iframe 不能删。
2. **聊天流式渲染靠手工 DOM diff**：`messageNode` / `traceEntries` / 工具卡 / todo 卡 / 审批卡各自拼字符串，状态变化靠人记得调用对应 render。
3. **测试锁实现、不锁行为**：框架迁移会让 45 组测试大面积失效，但它们本来也抓不到「流式块错位」「设置保存后不刷新」这类真实回归。
4. **没有类型与模块边界**：API 字段改名、事件字段变化只能靠运行时发现。
5. **没有真正的开发态**：无 HMR、无 source map、无组件预览；改一个设置表单要整页刷新并重新点路径。

## 3. 换框架的收益

| 现状痛点 | Vue/React 能解决什么 | 预期结果 |
| --- | --- | --- |
| 两套前端 + iframe | 设置页迁进同一套组件与路由，删除 `/classic` 依赖 | 旧 `app.js` 16.8k 行可退场，只保留一套设计系统 |
| 手写 DOM / 事件重绑 | 声明式模板 + 响应式状态，事件随组件生命周期 | 渲染代码显著变短，漏解绑/重复绑定的问题减少 |
| 流式块手工 diff | 以 `block.id` 为 key 的组件列表，只更新变化的块 | 聊天时间线更可预测；配合虚拟滚动可支撑长会话 |
| 状态散落 | Pinia store 按领域拆分（会话/设置/团队/工单/画布） | 状态变更可追踪，跨页面复用 |
| API 字段漂移 | TypeScript + 由 FastAPI `/openapi.json` 生成类型 | 后端改字段时前端编译期报错 |
| 测试脆弱 | Vitest 组件测试 + Playwright 真浏览器 E2E | 从「源码里有没有这个字符串」升级为「用户能不能完成这件事」 |
| 无构建 | Vite HMR、按需加载、哈希文件名、tree-shaking | 开发循环更快；首屏不必加载 CodeMirror 等重资源 |
| 手写缓存戳 | Vite 内容哈希 | 不再手动改 `?v=`，也不会漏改 |
| 无类型 | TS + ESLint + `vue-tsc` | 重构敢动，CI 能挡住低级错误 |

### 3.1 不要误解「npm 开发」

- **Node 只在构建期需要**，运行时仍然是 FastAPI 托管静态文件，桌面端仍然离线可用；
- 不需要 SSR，不需要 Next/Nuxt；本地 SPA + Vite 静态产物即可；
- 引入 npm 不等于引入运行时网络依赖；所有包都打进产物，禁止 CDN；
- 框架运行时体积（Vue ~35 KB gzip 量级）对本地应用可以忽略，换来的组件化收益更大。

## 4. 代价与风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 迁移工作量大 | 新壳 + 设置页完整对齐，约 **30–45 人日**（见 §7） | 分阶段，不一次性重写；先壳与设置，后聊天 |
| 聊天流式回归 | 最高风险区：SSE、工具卡、审批、todo、附件、Markdown | 先补 Playwright 关键链路，再迁移；保留旧版可回退 |
| 测试重写 | 45 组文本断言不能直接复用 | 不逐条移植；用 Vitest + Playwright 重建行为覆盖 |
| 供应链 | `node_modules`、锁文件、审计、构建可复现 | 提交 `package-lock.json`；CI 用 `npm ci`；固定 Node 版本；定期 `npm audit` |
| 打包链路 | PyInstaller 可能收到过期或缺失的 `dist` | 打包脚本强制 `npm ci && npm run build`，并检查 `web/dist/index.html` |
| 静态资源路径冲突 | 旧 `/assets` 挂载与 Vite 默认 `assets/` 冲突 | 迁移期 Vite 用 `build.assetsDir = 'static'`；切换后再统一 |
| WebView 兼容 | macOS WKWebView / Windows WebView2 对现代语法支持不一 | Vite `build.target = 'es2020'`；CI 在桌面壳里做冒烟 |
| 开发态原生桥 | `window.pywebview.api` 在 Vite dev server 中不存在 | 抽 `native.ts` 适配层，浏览器态降级；桌面态冒烟覆盖 |
| 短期交付变慢 | 3.7 期间功能冻结或减半 | 把 3.7 定位为「基础设施 + 壳 + 设置」，功能需求排到 3.8 |

## 5. Vue 还是 React

### 5.1 推荐：Vue 3 + Vite + TypeScript

| 维度 | Vue 3 | React |
| --- | --- | --- |
| 与现有 HTML 字符串的迁移距离 | 模板接近现有结构，CSS 可沿用 | JSX 需要重写结构，但更灵活 |
| 表单/设置页 | `v-model` 心智负担低 | 受控组件样板更多 |
| 流式列表 | 响应式系统 + keyed `v-for` 直接 | 需要 `memo` / 外部 store 控制重渲染 |
| 运行时体积 | 较小 | 稍大（可接受） |
| 生态 | 足够（Pinia、Vue Router、VueUse） | 更大，招聘/资料更多 |
| 单人/小团队 | 更省样板 | 需要更多约定 |
| AI 编码助手熟悉度 | 高 | 最高 |

**结论**：没有既有 React 团队偏好时，选 Vue 3。若团队已经重度使用 React，选 React 也完全可行；关键是**只选一个**，不要把两套运行时都带进来。

### 5.2 明确不选

- **不选 Next/Nuxt**：没有 SEO、没有服务端渲染需求，SSR 只会增加打包与部署复杂度。
- **不选重型 UI 库**（Element Plus / Ant Design 等）作为主骨架：当前是自定义 IM 视觉，套组件库会陷入覆盖样式的长期战争；最多用 headless 原语（弹层、焦点管理、虚拟列表）。
- **不把 Tailwind 作为迁移前置条件**：先沿用现有 CSS 变量与类名，迁移稳定后再决定是否引入原子化 CSS。

## 6. 推荐架构

```text
frontend/
  index.html
  vite.config.ts
  package.json
  tsconfig.json
  src/
    main.ts
    App.vue
    router.ts
    api/
      client.ts          # fetch 封装、错误归一、SSE
      types.ts           # 由 /openapi.json 生成或手写
    stores/
      session.ts         # 当前用户/主题/布局
      conversations.ts
      teams.ts
      roles.ts
      workspaces.ts
      work.ts
      settings.ts
    composables/
      useRunStream.ts    # EventSource 生命周期、断线重连、清理
      useTheme.ts
      useI18n.ts
      useNative.ts       # pywebview 桥 + 浏览器降级
    components/
      shell/             # rail / 全宽 canvas / 右侧聊天抽屉
      chat/              # timeline / message / tool / todo / approval / ask
      settings/          # models / subscriptions / mcp / skills / appearance
      team/ role/ workspace/ work/ canvas/
    styles/
      tokens.css         # 现有主题变量
      base.css
```

### 6.1 关键设计

- **流式渲染**：`useRunStream` 管理 `EventSource`，组件卸载时 `close()`；时间线按 `block.id` 做 keyed 渲染；大对象用 `shallowRef` / `markRaw`，避免深度代理拖慢流式更新。
- **状态边界**：Pinia 按领域拆 store；组件不直接改别的 store 的内部字段，跨域动作走 action。
- **API 类型**：优先用 `openapi-typescript` 从 FastAPI `/openapi.json` 生成 `types.ts`，CI 检查 diff；至少先覆盖会话、团队、设置三组高频接口。
- **Markdown**：`markdown-it` + `DOMPurify`（或等价 sanitizer）。模型输出是不可信内容，必须默认转义/清洗；代码高亮按需加载。
- **代码查看**：CodeMirror 6 通过 npm 引入，路由级动态 import，替代当前 vendored CodeMirror 5。
- **主题/i18n**：沿用现有 CSS 变量；i18n 用 `vue-i18n` 或轻量字典，先把 `team.*` 等未启用文案接上。
- **原生桥**：`useNative` 统一封装文件夹选择、打开数据目录、退出；dev 态降级为 `<input type="file" webkitdirectory>` 或提示。
- **错误边界**：全局 `app.config.errorHandler` + 路由级错误页；流式连接断开时给出可恢复提示。

### 6.2 后端托管

迁移期建议保留旧入口作为回退：

```text
/            -> web/dist/index.html（新 SPA）
/classic     -> 旧设置页（迁移完成前）
/api/...     -> FastAPI（不变）
/static/...  -> Vite 产物（避免与旧 /assets 冲突）
```

SPA fallback 必须放在 API、health、static 之后，否则会把 404 的接口请求也返回 `index.html`。切换完成后删除 `/classic` 与旧 `web/assets/`，只保留 `web/dist`。

## 7. 迁移路线（建议）

### 7.1 阶段与估算

| 阶段 | 内容 | 产出 | 估算 |
| --- | --- | --- | --- |
| P0 基础设施 | Vite/TS/ESLint/Vitest/Playwright；API client；主题 token；dev proxy；CI | 能跑空壳与健康检查 | 2–3 人日 |
| P1 壳与列表 | rail / 全宽 canvas / 右侧聊天抽屉 / 路由 / 主题 / i18n；会话、工作区、角色、群组卡片 | 新壳可导航，旧壳仍可回退 | 4–6 人日 |
| P2 设置迁移 | 模型/订阅/工作区/用量/MCP/技能/外观/工具/运行时；删除 iframe | **旧前端 16.8k 行可退场** | 8–12 人日 |
| P3 聊天核心 | SSE、时间线、工具卡、todo、审批、ask_user、附件、Markdown、队列、停止 | 主路径可用 | 10–15 人日 |
| P4 其余与收尾 | 工单/看板、执行画布、组织/部门、原生桥、打包、E2E 补齐 | 全量对齐，删除 `/classic` | 5–8 人日 |

合计约 **29–44 人日**。一个人做，按 60%–70% 有效开发时间，约 **6–9 周**；两人并行可压缩到 4–6 周，但聊天与设置不建议由不同人同时改同一套 API 契约。

> 估算是工程量级，不是承诺；实际取决于设置页字段量和聊天边角回归。

### 7.2 3.7.0 的建议范围

**推荐把 3.7.0 定义为「框架化 + 新壳 + 设置迁移」：**

- P0 + P1 + P2；
- 聊天继续用现有实现，通过路由/入口共存；
- 3.8.0 完成聊天核心迁移；
- 3.9.0 删除旧前端、补 E2E、完成打包收尾。

这样 3.7.0 的可见成果是「一套代码、设置不再 iframe、开发有 HMR」，而不是「所有功能重写但回归没底」。

### 7.3 如果 3.7.0 必须一次到位

只有在满足以下条件时才建议：

1. 先补齐 8–10 条 Playwright 关键链路（建会话、发消息、流式、审批、提问、设置保存、群成员、附件、主题、打包冒烟）；
2. 功能冻结，按「功能 parity 清单」逐项勾选；
3. 保留旧入口至少一个版本，可一键回退；
4. 排期按 6–9 周准备，不按 2–3 周。

否则「大版本一次切换」的收益会被回归和延期吃掉。

## 8. 打包与「只有指定才打包」

这个方向**同意**，但要把两个「打包」分开：

| 动作 | 命令 | 频率 | 是否必须 |
| --- | --- | --- | --- |
| 前端开发 | `npm run dev` | 每次开发 | 是 |
| 前端构建 | `npm run build` | 每次发布/CI | 是（秒级到十几秒） |
| 桌面应用打包 | `bash desktop/build_macos.sh` | 仅 Release / 手动 | 否，按需 |

建议的流程：

```bash
# 日常开发：Vite HMR + 代理到本地 FastAPI
npm run dev

# CI 质量门禁：不生成 dmg
npm ci
npm run lint
npm run typecheck
npm run test:unit
npm run build
pytest / frontend E2E

# 指定发布：才做慢打包
bash desktop/build_macos.sh   # 内部执行 npm ci && npm run build，再 PyInstaller
```

关键约束：

- `desktop/build_macos.sh` / `AtlasX.spec` 必须依赖 `web/dist`，并在缺失时**失败或自动构建**，不能静默收旧产物；
- 打包前写入构建戳（`VERSION` + git sha + 构建时间），运行时「关于」可核对；
- `node_modules/` 不进仓库；`package-lock.json` 必须进仓库；Node 版本用 `.nvmrc` / `engines` 固定；
- 生产构建关闭 source map（或只上传不随包分发），避免把源码打进 dmg；
- 桌面冒烟仍保留：启动、打开窗口、发一条消息、打开设置、退出。

## 9. 测试策略

| 层级 | 工具 | 覆盖 |
| --- | --- | --- |
| 单元 | Vitest | store、composable、格式化、Markdown 清洗、权限判断 |
| 组件 | Vitest + Vue Test Utils | 设置表单、工具卡、审批卡、todo 卡、群成员弹框 |
| E2E | Playwright | 建会话 → 发消息 → 流式完成；审批/提问；设置保存；群 CRUD；附件；主题；打包冒烟 |
| 视觉 | Playwright screenshot | 主壳、会话列表、聊天、设置、窄屏；只对稳定区域做 diff |

明确**不要**把现有 45 组「源码里有没有这个函数名」逐条翻译成 Vue 版本；那只会把旧债带进新栈。保留少量结构断言即可，行为覆盖交给组件测试和 E2E。

## 10. 验收清单（迁移完成的定义）

- [ ] `web/` 只保留一套前端源码与一套构建产物，`/classic` 与 `web/assets/app.js` 删除；
- [ ] 设置页不再 iframe，所有 tab 在新栈内可保存并刷新；
- [ ] 聊天主路径：流式、工具卡、todo、审批、ask_user、附件、Markdown、停止、队列全部对齐；
- [ ] 群聊、单聊、@成员、未读、系统消息对齐；
- [ ] 工单、执行画布、组织/部门、工作区文件预览对齐；
- [ ] 主题/语言/布局偏好跨重启保留；
- [ ] `npm ci && npm run build` 可在干净环境复现；
- [ ] PyInstaller 打包包含最新 `web/dist`，桌面冒烟通过；
- [ ] CI 默认不产 dmg；Release 才产 dmg；
- [ ] 关键 E2E 全绿，且没有依赖「源码字符串」的测试作为唯一保障。

## 11. 最终判断

**总体上更优，建议做，但要换一种做法。**

- **值得做的理由**：两套前端、iframe 设置页、手写 DOM、文本断言测试，这四项的组合成本已经超过框架的引入成本；框架化能一次性解决「重复实现 + 不可测 + 难重构」。
- **必须避免的做法**：把 3.7.0 当成「停旧写新、一次性切换」。在没有 E2E 和 parity 清单的情况下，聊天流式与设置保存是最容易回归的两块。
- **推荐决策**：
  1. 选 **Vue 3 + Vite + TypeScript + Pinia + Vue Router**；
  2. 3.7.0 先交付「基础设施 + 新壳 + 设置迁移」，聊天在 3.8 完成；
  3. 从第一天就补 Playwright，不移植源码文本测试；
  4. 打包与前端构建分离：日常 HMR，CI 只构建，Release 才出 dmg；
  5. 迁移期保留 `/classic` 回退，切换稳定后立即删除旧前端。

如果团队只有一个人、且 3.7.0 的时间窗口小于 3 周，那么**不建议在 3.7.0 做完整框架化**；可以先做 P0（Vite + TS + 测试基础设施）和设置页迁移，把风险最高的聊天留到下一个版本。这仍然比继续在 5.7k 行 IIFE 上叠功能更优。
